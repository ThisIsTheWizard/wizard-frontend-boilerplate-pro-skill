## 1. When to use v3 instead of v4

The skill defaults to Tailwind v4. Use this reference **only** when:

- The user explicitly chooses v3 during Phase 1 interview.
- The framework version the user selected has a known v4 incompatibility (check
  `references/tailwind/per-framework-gotchas.md`).
- An existing project is being extended rather than scaffolded fresh, and it
  already runs v3 — a mid-project upgrade would be out of scope.

All other cases: use `references/tailwind/v4-setup.md`.

---

## 2. Install

All frameworks use PostCSS in v3 — there is no dedicated Vite plugin.

```bash
<package-manager> add -D tailwindcss@3 postcss autoprefixer
```

> Pin the major to `3` (`tailwindcss@3`) so `<resolved-version>` from
> `check_versions.sh` is the latest 3.x patch, not v4. The `autoprefixer`
> package is required in v3; do **not** omit it.

## 3. tailwind.config.ts

Create at the project root. Use TypeScript — it gives autocomplete and keeps
the project consistent with a TS-first setup.

```ts
import type { Config } from "tailwindcss";

const config: Config = {
  content: [
    "./src/**/*.{js,ts,jsx,tsx,vue,svelte}",
    "./index.html",
    "./app/**/*.{js,ts,jsx,tsx}",
    "./pages/**/*.{js,ts,jsx,tsx}",
    "./components/**/*.{js,ts,jsx,tsx}",
  ],
  darkMode: "class",
  theme: {
    extend: {},
  },
  plugins: [],
};

export default config;
```

### content array — per framework

Adjust the `content` paths to match the framework's file layout:

| Framework | Paths to include |
|---|---|
| Next.js (App Router) | `./src/app/**/*.{js,ts,jsx,tsx}`, `./src/components/**/*.{js,ts,jsx,tsx}` |
| React + Vite | `./index.html`, `./src/**/*.{js,ts,jsx,tsx}` |
| Vue | `./index.html`, `./src/**/*.{js,ts,vue}` |
| Nuxt | `./app/**/*.{js,ts,vue}`, `./components/**/*.{js,ts,vue}`, `./layouts/**/*.vue`, `./pages/**/*.vue` |
| SvelteKit | `./src/**/*.{html,js,ts,svelte}` |

> v3 does **not** auto-detect files. Missing a path means Tailwind silently
> purges classes used in that directory. Double-check the content array before
> reporting setup complete.

## 4. PostCSS config

Create `postcss.config.mjs` at the project root:

```js
/** @type {import('postcss').Config} */
const config = {
  plugins: {
    tailwindcss: {},
    autoprefixer: {},
  },
};

export default config;
```

> Unlike v4, v3 uses the `tailwindcss` package directly as a PostCSS plugin
> (not `@tailwindcss/postcss`). `autoprefixer` is also required here.

### Nuxt-specific note

Nuxt has a built-in PostCSS pipeline. Add Tailwind via `nuxt.config.ts`
instead of a standalone `postcss.config.mjs`:

```ts
export default defineNuxtConfig({
  postcss: {
    plugins: {
      tailwindcss: {},
      autoprefixer: {},
    },
  },
});
```

## 5. CSS entry-point

Use the three-directive form — not the single `@import "tailwindcss"` from v4.

| Framework | CSS entry file |
|---|---|
| Next.js | `src/app/globals.css` |
| React + Vite | `src/index.css` |
| Vue | `src/assets/main.css` |
| Nuxt | `assets/css/main.css` |
| SvelteKit | `src/app.css` |

```css
@tailwind base;
@tailwind components;
@tailwind utilities;

@import "./tokens.css";
```

> Keep `@import "./tokens.css"` after the Tailwind directives so token
> declarations do not get overridden by Tailwind's base reset.

> Do **not** use `@import "tailwindcss"` — that is the v4 syntax and will
> produce an error in v3.

## 6. theme.extend — design tokens

v3 does not have a `@theme` block. Design tokens are declared in
`tailwind.config.ts` under `theme.extend`, and runtime semantic values
(light/dark swaps) live in `:root` / `.dark` CSS.

### tokens.css (generated by generate_palette.py)

```css
:root {
  /* Palette scale — raw values (neutral) */
  --color-neutral-50: #f8fafc;
  --color-neutral-100: #f1f5f9;
  /* … 50–950 … */
  --color-neutral-950: #020617;

  /* Palette scale — raw values (accent) */
  --color-accent-50: #eef2ff;
  /* … */
  --color-accent-950: #1e1b4b;

  /* Semantic tokens — light mode */
  --background: var(--color-neutral-50);
  --foreground: var(--color-neutral-950);
  --surface: var(--color-neutral-100);
  --border: var(--color-neutral-200);
  --primary: var(--color-accent-500);
  --primary-foreground: var(--color-neutral-50);
  --muted: var(--color-neutral-400);
}

.dark {
  --background: var(--color-neutral-950);
  --foreground: var(--color-neutral-50);
  --surface: var(--color-neutral-900);
  --border: var(--color-neutral-800);
  --primary: var(--color-accent-400);
  --primary-foreground: var(--color-neutral-950);
  --muted: var(--color-neutral-500);
}
```

> In v3, `generate_palette.py` outputs hex values rather than OKLCH — v3's
> CSS variable support is fine, but OKLCH browser coverage was limited when v3
> was the current major. The script detects the target Tailwind version and
> adjusts output format accordingly.

### tailwind.config.ts — wiring CSS vars to utilities

Register the palette as Tailwind utilities by referencing the CSS variables in
`theme.extend.colors`:

```ts
import type { Config } from "tailwindcss";

const config: Config = {
  content: ["./src/**/*.{js,ts,jsx,tsx,vue,svelte}", "./index.html"],
  darkMode: "class",
  theme: {
    extend: {
      colors: {
        neutral: {
          50: "var(--color-neutral-50)",
          100: "var(--color-neutral-100)",
          200: "var(--color-neutral-200)",
          300: "var(--color-neutral-300)",
          400: "var(--color-neutral-400)",
          500: "var(--color-neutral-500)",
          600: "var(--color-neutral-600)",
          700: "var(--color-neutral-700)",
          800: "var(--color-neutral-800)",
          900: "var(--color-neutral-900)",
          950: "var(--color-neutral-950)",
        },
        accent: {
          50: "var(--color-accent-50)",
          100: "var(--color-accent-100)",
          200: "var(--color-accent-200)",
          300: "var(--color-accent-300)",
          400: "var(--color-accent-400)",
          500: "var(--color-accent-500)",
          600: "var(--color-accent-600)",
          700: "var(--color-accent-700)",
          800: "var(--color-accent-800)",
          900: "var(--color-accent-900)",
          950: "var(--color-accent-950)",
        },
        background: "var(--background)",
        foreground: "var(--foreground)",
        surface: "var(--surface)",
        border: "var(--border)",
        primary: "var(--primary)",
        "primary-foreground": "var(--primary-foreground)",
        muted: "var(--muted)",
      },
    },
  },
  plugins: [],
};

export default config;
```

This wiring means `bg-background`, `text-foreground`, `border-border`, etc. all
work as utility classes and resolve to the correct CSS variable at runtime —
the same authoring experience as v4, just via JS config rather than `@theme`.

## 7. Color token integration

Components consume semantic tokens via CSS variables or the extended utilities.

```html
<!-- Via extended utility (preferred) -->
<div class="bg-background text-foreground border-border">…</div>

<!-- Via arbitrary value (fallback) -->
<div class="bg-[var(--background)] text-[var(--foreground)]">…</div>
```

Both forms work in v3. The extended utility form is preferred because it gives
tree-shakeable purge hints — v3's content scanner can see `bg-background` and
keep it; `bg-[var(--background)]` in an arbitrary value is always kept.

## 8. Dark mode strategy

v3 requires `darkMode: "class"` in `tailwind.config.ts` (already included in
the config above). The ThemeProvider in `assets/theme-provider/` toggles
`document.documentElement.classList` between `""` and `"dark"`.

### Inline usage

```html
<!-- Explicit dark variant -->
<div class="bg-white dark:bg-surface">…</div>

<!-- Semantic token (no dark: variant needed) -->
<div class="bg-background">…</div>
```

> Prefer semantic tokens. They avoid `dark:` duplication and keep component
> code identical to v4 output — easier to upgrade later.

## 9. Utility class notes

A few classes were renamed between v3 and v4. When writing components for v3,
use the v3 names:

| v3 class | v4 equivalent | Note |
|---|---|---|
| `flex-shrink-0` | `shrink-0` | v3 ships both; `flex-shrink-0` is canonical |
| `flex-grow` | `grow` | v3 ships both; `flex-grow` is canonical |
| `overflow-ellipsis` | `text-ellipsis` | v3 uses `overflow-ellipsis` |
| `transform` (bare) | not needed | Required in v3 to activate transform utilities |
| `filter` (bare) | not needed | Required in v3 to activate filter utilities |
| `backdrop-filter` (bare) | not needed | Required in v3 to activate backdrop utilities |
| `decoration-clone` | `box-decoration-clone` | v3 uses `decoration-clone` |

> Always add the bare `transform`, `filter`, and `backdrop-filter` classes when
> using their associated utilities in v3. Omitting them is the most common
> cause of "class not working" bugs when authoring v3 components.

## 10. Verification

After completing setup, run the dev server and confirm:

```bash
<package-manager> dev
```

In browser dev tools console:

```js
// Should return a hex string, not an empty string
getComputedStyle(document.documentElement).getPropertyValue("--color-neutral-500").trim();
```

In the Elements panel, inspect a utility-classed element (e.g. `class="bg-background"`).
Computed styles should show the CSS variable value, not `initial`.

If Tailwind classes are not applied:

1. Confirm the CSS entry file uses `@tailwind base/components/utilities` — not
   `@import "tailwindcss"`.
2. Confirm `tailwind.config.ts` exists and its `content` array covers all
   relevant source file paths.
3. Confirm `postcss.config.mjs` lists both `tailwindcss` and `autoprefixer`.
4. Confirm `darkMode: "class"` is set in the config — omitting it disables
   `dark:` variants entirely.
5. Open the build output CSS and search for a known utility class (e.g.
   `bg-background`) — if absent, a `content` path is missing.
